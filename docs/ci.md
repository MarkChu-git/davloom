# CI

GitHub Actions runs Davloom's checks on every pull request, whatever its base branch, and on every push to `main`. The workflow has no branch filter because stacked pull requests target each other's branches until GitHub retargets them to `main`. Every job calls a command that also runs on a contributor's machine, so a failed job can be reproduced locally with the command in the table below. The plan behind this layout is the OpenSpec change `add-ci-baseline`.

## Jobs

`.github/workflows/ci.yml` holds the jobs. Each runs on `ubuntu-24.04` with a 20-minute timeout and starts with the local action `.github/actions/setup`. A newer push to the same pull request or branch cancels the run in progress.

| Job            | What it runs                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Local command                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`        | Lint with the type-aware rules, the format check, the check that Astryx and StyleX are pinned and in range, the generated theme check, the typecheck, the unit tests and the production builds                                                                                                                                                                                                                                                                   | `bun run check`                                                                                                                                                   |
| `compat`       | The check that passes when every `compat (…)` suite and `ui` shard passed. Each suite is a job of its own: five shards of the HTTP compatibility tests on Bun and workerd, with the real clients and the log redaction check, Better Auth and the database upgrades on D1 and Bun SQLite, the unit tests of `packages/core` in workerd, the storage contract, the S3 driver against RustFS, the brand change check and the Cloud Free tests that need no account | `bun run --filter @davloom/compat-tests test:without-ui`                                                                                                          |
| `ui`           | The Playwright tests against the production build, in Chromium, Firefox and WebKit, with the axe-core audit, in six shards that run side by side                                                                                                                                                                                                                                                                                                                 | `bun run --filter @davloom/compat-tests playwright:install` once, then `bun run --filter @davloom/compat-tests test:ui`                                           |
| `coverage`     | The unit tests with Istanbul coverage and the per-package thresholds, then each package's coverage in the job summary                                                                                                                                                                                                                                                                                                                                            | `bun run test:coverage`, then `bun run coverage:summary`                                                                                                          |
| `dependencies` | OSV-Scanner on every package in `bun.lock`, transitive ones included                                                                                                                                                                                                                                                                                                                                                                                             | `bun run scan:deps`                                                                                                                                               |
| `secrets`      | Gitleaks on the commits a pull request adds, or on the history of `main` after a push to it                                                                                                                                                                                                                                                                                                                                                                      | `bun run scan:secrets --log-opts=origin/main..HEAD` for the commits not yet on `main`, or `bun run scan:secrets --log-opts=origin/main` for the history of `main` |
| `workflows`    | actionlint on the workflows, then zizmor on the workflows and the local actions                                                                                                                                                                                                                                                                                                                                                                                  | `bun run scan:actionlint`, then `bun run scan:zizmor`                                                                                                             |
| `laws`         | Compiles every Bend module with the pinned Bend, fails when a committed `src/compiled/*.mjs` differs, and runs `bend PROOF.bend` plain and with `--verdict`                                                                                                                                                                                                                                                                                                      | `bun run laws:setup` once, then `bun run laws:check`                                                                                                              |
| `quota`        | The Cloud Free quota check: the production Worker in local workerd with its D1, Durable Object and fetch bindings metered, each WebDAV and API request held to the Free plan's limits per invocation and to its measured budget, and a modeled day held to the daily quotas                                                                                                                                                                                      | `bun run --filter @davloom/compat-tests test:quota`                                                                                                               |

The setup action first puts `.github/actions/setup/no-node` at the front of `PATH`. A step that calls `node`, or starts a launcher whose shebang names Node, then fails instead of running the Node that the runner image ships. The action then installs the Bun release that `packageManager` in `package.json` names and runs `bun install --frozen-lockfile --ignore-scripts`. The scan jobs and CodeQL pass `install: "false"` and skip the install: the scans only run a pinned CLI, and CodeQL's extractor reads one file at a time and skips `node_modules`.

The `laws` job runs `bun run laws:setup`, with the Bend and Lean toolchain cached, and then `bun run laws:check`. It is a required check: no pull request merges with a law that does not hold, a proof that fails, or a compiled module that differs from its source. Locally, `bun run laws:build` rewrites the compiled modules after a change to a `.bend` file, and `bun run laws:proofs` rewrites `PROOF.bend` from `LAWS.bend` and the hand-written proofs in `packages/laws/proofs/`.

`.github/workflows/deploy.yml` deploys every push to `main`, and a manual run, to the project's Cloudflare Workers Free account: it builds the Dashboard, applies the D1 migrations and runs `wrangler deploy` from `apps/api`. It reads the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in the `production` environment, and no pull request runs it; `scripts/workflow-secrets.test.ts` keeps it that way. The Worker itself needs the Workers secrets `DAVLOOM_SECRET` (at least 32 bytes), set once with `wrangler secret put`. Registration is open until the first account exists, so whoever deploys a new instance registers its owner right away.

The HTTP shards of `compat` also install litmus, rclone, cadaver and davfs2 from Ubuntu's archive, and each client runs against the production Worker in local workerd and against the self-hosted Bun server with RustFS in Docker. `http/clients.test.ts` runs every litmus suite and a set of rclone transfers. `http/cadaver.test.ts` runs scripted cadaver sessions: put, mput, get, mget, cat, ls, mkcol, move, copy, delete, rmcol, lock and unlock, propset, propget and propdel, and a Read Only key's refusals. `http/davfs2.test.ts` mounts the Mount with davfs2 and works through the file system: writing, reading, stat, mkdir, rename, overwrite, append, copy, unlink, rmdir, readdir, `rm -r`, the lock davfs2 takes on a file open for writing, the uploads that unmounting finishes, and a Read Only mount. Mounting needs root, which the runner's passwordless sudo gives; the tests run `mount.davfs` and `umount` through `sudo -n`, or directly when they already run as root. Every case reads what the server holds over HTTP instead of trusting the client's report. A machine without a client, without Docker, or for davfs2 without `/dev/fuse` and such sudo, skips the cases it cannot run. `test:storage` runs the storage contract against the Durable Objects adapter in workerd.

`.github/workflows/dependency-scan.yml` runs the dependency scan on `main` every Monday at 04:23 UTC, so a vulnerability published for a dependency already on `main` fails a run even when no pull request is open. A maintainer can start it by hand from the Actions tab or with `gh workflow run dependency-scan.yml`.

`.github/workflows/codeql.yml` runs CodeQL's JavaScript and TypeScript analysis on every pull request, on every push to `main` and every Tuesday at 04:37 UTC, because new CodeQL releases bring new queries. Its one job is the only one in the repository granted a write permission, `security-events: write`, which uploads the results to code scanning; they appear under Security, Code scanning, and on the pull request. CodeQL's TypeScript extractor starts its parser with the `node` on `PATH` unless `SEMMLE_TYPESCRIPT_NODE_RUNTIME` names another runtime, so the job sets it to `bun` and keeps the setup action's guard, which fails every call to `node`. CodeQL has no local command.

Three more checks run inside those suites. `upgrade/` (in the `d1` and `bun-sqlite` suites) starts a database at each older migration set of `packages/database/drizzle`, 0000 up to the one before the latest, fills every table those migrations made, upgrades it the way a deployment does (applyD1Migrations, which follows `wrangler d1 migrations apply`, on D1 in workerd, and the Drizzle migrator that the Bun entry runs, on a Bun SQLite file), and checks that the rows survive and the schema equals a new install's; a migration without sample rows in `upgrade/samples.ts` fails it. `http/log-redaction.test.ts` sends both API Keys, wrong and forged credentials, the session cookie, passwords and tokens in bodies, the export key and an S3 secret key to the Worker, Bun with SQLite and Bun with RustFS, and fails when any of them appears in what the server logs. `ui/accessibility.spec.ts` and the `Accessibility:` cases of `ui/dashboard.spec.ts` run axe-core's WCAG 2.2 A and AA rules and its best practices on every page state, signed in and signed out, in light and dark mode, in desktop Chromium; `ui/axe.ts` lists the two findings it lets through, each for one element and a reason.

`.github/workflows/release.yml` builds, smoke-tests, scans and publishes the Docker image for each `v*` tag, attests it and creates the GitHub Release; `docs/deployment/release.md` describes its jobs, the local commands for each step, and how to roll a release back. A pull request that changes the image, its scripts or the workflow runs its build, smoke test and scans and publishes nothing. It is not a required check, because it runs only for those pull requests, and GitHub waits forever for a required check that does not report.

## Cloud Free quota check

The `quota` job runs `tests/integration/compat/quota/quota.test.ts` against `quota/entry.workers.ts`: the production entry of `apps/api` with its `DB` binding, its `STORAGE` namespace and `fetch` wrapped by `quota/meter.workers.ts`, which counts D1 statements, D1 calls and the rows D1 reports, calls on Durable Object stubs and the SQLite rows the objects report, and fetches to the internet. The domain code is unchanged; `/__quota/usage` answers what the request before it cost. Each case checks one request against the Free plan's limits per invocation (50 D1 queries, 1,000 internal and 50 external subrequests) and against the budget measured for it on 2026-11-24, so a change that adds a query fails until its budget moves in the same pull request. Listings, copies and moves of 1, 49, 51 and 120 files check that the queries and object calls of a request do not grow with a collection. A modeled day of one active user (a client that checks a folder every minute for 12 hours with a cold API Key cache, a few hundred edits, the Dashboard now and then) must fit ten times into each daily quota: 100,000 Worker requests, 5 million rows read and 100,000 written in D1, and 100,000 requests, 5 million rows read and 100,000 written in Durable Objects. The test writes the measurements and the model to `tests/integration/compat/test-results/quota/results.json`.

On 2026-11-24 the modeled day cost 3,301 Worker requests and 6,843 Durable Object requests, so the Durable Object request quota binds first, at 14 such users; D1 rows written allow 246. The first run found that a Depth 1 PROPFIND read the locks of each entry with a query of its own, so a listing of about 50 entries passed the 50-query limit; it now reads them once. `/api/overview` and `/api/backends` read a backend's usage from running totals, a few rows whatever the backend holds, and a test holds them flat as files are added. CPU time is not measured locally; the Cloud Free tests on a real deployment measure it.

## Load test

`.github/workflows/load.yml` runs Grafana k6 every Thursday at 03:17 UTC and by hand (`gh workflow run load.yml`), against the production Worker in local workerd, never against Cloud Free (PRD §11). It is not a required check. `tests/integration/compat/scripts/load.ts` starts the Worker with an administrator and an API Key and runs `tests/integration/compat/load/davloom.js` in the pinned k6 image, with the host's network on Linux and `host.docker.internal` under Docker Desktop. Six virtual users each loop PUT (64 KiB), GET, PROPFIND Depth 1 on their own collection of about 20 files, LOCK, UNLOCK, MOVE and DELETE, and two loop `/api/me`, `/api/overview`, `/api/keys` and `/api/mounts`, ramping up for 20 s, holding for 90 s and ramping down for 10 s. The run fails when more than 1% of requests or checks fail or an operation's 95th percentile passes its threshold, and the job's summary shows each operation's median, p95 and maximum.

| Command                                            | What it runs                                           |
| -------------------------------------------------- | ------------------------------------------------------ |
| `bun run --filter @davloom/compat-tests test:load` | Builds the Dashboard, then the load test; needs Docker |
| `bun tests/integration/compat/scripts/load.ts`     | The load test alone, after a Dashboard build           |

Two runs on a machine with 4 CPUs, as many as the runner has, failed no request and measured these 95th percentiles in ms: PUT 151 and 187, GET 79 and 108, PROPFIND 83 and 96, LOCK 78 and 108, UNLOCK 79 and 119, MOVE 94 and 131, DELETE 123, `/api/me` 84 and 98, `/api/overview` 90 and 118, `/api/keys` 85 and 110, `/api/mounts` 76 and 100. Each threshold is about 2.5 times the higher value, which leaves room for the runner, 1.5 to 1.8 times slower in the run times below. Measure again and move the thresholds in the same pull request when a change makes an operation slower on purpose.

## Mutation testing

`.github/workflows/mutation.yml` runs StrykerJS with its Vitest runner on `packages/core` and on `packages/webdav` every Wednesday at 03:41 UTC, one job per package, and fails a package's job when its mutation score is below 80% (PRD §11, Decision 14 of `add-phase-1-core`). A release needs a passing run on the commit it ships: start one from the Actions tab or with `gh workflow run mutation.yml`. The workflow is not a required check, because a run takes minutes per package.

| Command                      | What it runs                       |
| ---------------------------- | ---------------------------------- |
| `bun run test:mutation`      | Both packages, one after the other |
| `bun run test:mutation core` | `packages/core` only (or `webdav`) |

Stryker mutates each package's `src/**/*.ts` except its tests and its `test` and `testing` helpers, runs the package's tests through the package's own `vitest.config.ts`, prints a table of the scores by file, and writes an HTML and a JSON report to `reports/mutation/<package>/`, which Git ignores. `packages/<package>/stryker.config.ts` holds each run's options, from `scripts/mutation/stryker.ts`. A mutant that survives is a change to the code that no test notices: add a test that fails for it, with an expected value from the RFC or another source independent of the code. Do not exclude code from mutation to raise the score. Only a mutant that no input can tell apart from the original, an equivalent mutant, may be turned off, with `// Stryker disable next-line <mutator>: <why it is equivalent>` on the line above it.

StrykerJS supports Node only, so `scripts/mutation.ts` starts it on Bun with the four changes that Decision 15 of `add-phase-1-core` records: `plugins` names the Vitest runner by its path, because Bun's isolated install hides it from Stryker; `tsconfigFile` names a file that does not exist, which skips Stryker's rewrite of `tsconfig.json`, since TypeScript 7 lacks the API it uses; the preload `scripts/mutation/preload.ts` wraps `Error.prepareStackTrace` in Stryker's main process (oven-sh/bun#41151); and each package has a Vitest configuration that lists its tests. The preload also gives Stryker's logging server Node's fallback to 0.0.0.0 on a machine without IPv6, where Bun's `listen()` without a host fails with "Failed to listen at ::".

## Pinned tools

OSV-Scanner, Gitleaks, actionlint, zizmor, and the Trivy and Syft that the release workflow runs, are release binaries, not npm packages and not third-party actions (Decision 5 of `add-ci-baseline`). `scripts/lib/tools.ts` pins each one's version and the SHA-256 of its download for macOS and Linux on arm64 and x64. `bun scripts/tool.ts <name> [arguments]` downloads the build for the current machine once, fails without caching it when its SHA-256 differs from the pin, and runs it. The cache is `$DAVLOOM_TOOL_CACHE`, or `$XDG_CACHE_HOME/davloom/tools`, or `~/.cache/davloom/tools`, and every checkout shares it. A variable that is empty or holds a relative path counts as unset, as the XDG spec says for `$XDG_CACHE_HOME`, so a typo cannot put the cache under the current directory. `bun run laws:setup` adds the Bend 2.0.40 and Lean 4.34.0 that `packages/laws/toolchain.json` pins, and the `--verdict` kernel it builds with that Lean. On an M4 Pro the first four tools take 101.6 MiB, Bend 61.1 MiB, Lean 2.7 GiB and the kernel 3.2 MiB.

k6 runs as a container instead: `IMAGES` in `scripts/lib/tools.ts` pins Grafana's `grafana/k6` image by its release tag and the SHA-256 digest of the release's multi-platform index (2.4.0, `sha256:d41bb79c…`), and Docker checks every layer it pulls against that digest. The image is one of the release's official distributions, and the load test needs Docker for nothing else. To move it, take the newest release tag of `grafana/k6` on Docker Hub that is not a pre-release, and its digest from `docker buildx imagetools inspect grafana/k6:<version>` or Docker Hub's tag list.

To move a tool to a newer release, take the version from its latest GitHub release, not a pre-release, and the SHA-256 of each of the four downloads from the release's checksum file. GitHub shows the same value as the asset's digest (`gh api repos/<owner>/<repo>/releases/tags/<tag> --jq '.assets[] | [.name, .digest]'`), which is the only source for a release without a checksum file.

## Required checks

Since 2026-11-20 the `main` Ruleset requires `check`, `compat`, `coverage`, `workflows`, `secrets` and `dependencies` to pass, and since then also `laws` and `quota`, as the GitHub Actions app reports them, and holds a pull request back until CodeQL has analyzed it and found no alert at High or higher and no error (Decision 6 of `add-ci-baseline`). Nobody can bypass `main`, the owner included. The `main reviews` Ruleset asks for two approvals, which repository admins bypass on pull requests only. A branch does not have to be up to date with `main` to merge.

`.github/rulesets/main.json` and `.github/rulesets/main-reviews.json` hold both Rulesets without the fields that GitHub sets itself, so `gh api -X PUT repos/MarkChu-git/davloom/rulesets/<id> --input <file>` sets either one back to its file: `main` is 26707024 and `main reviews` is 26707027. A deleted Ruleset comes back with `gh api -X POST repos/MarkChu-git/davloom/rulesets --input <file>`, under a new ID that then replaces the old one in this paragraph. Keep each file in step with its Ruleset on GitHub. `scripts/rulesets.test.ts` fails when the required checks and the jobs of `ci.yml` drift apart, when another workflow has a job with a required check's name, when a required job gets a job-level `if:`, a matrix or a reusable workflow, or when `ci.yml` or `codeql.yml` stops running on every pull request.

`.github/rulesets/main.json` names `quota` from the pull request that adds the job, because `scripts/rulesets.test.ts` asks the file to name every job of `ci.yml`; the Ruleset on GitHub takes it with `gh api -X PUT` once the job has run on `main`. GitHub waits for each required check by name, and a check that never reports blocks the pull request. To rename or remove a job, first drop it from the Ruleset on GitHub, then merge the pull request that changes `ci.yml` and the file. Require a new name only after its job has run on `main`.

## Running CI's commands locally

Install the way CI does:

```bash
bun install --frozen-lockfile --ignore-scripts
```

A frozen install fails when `package.json` and `bun.lock` disagree, locally as in CI. `--ignore-scripts` skips the postinstall of `workerd`, the one dependency script that Bun would run, which calls Node and which nothing needs.

To catch a call to Node before CI does, put the same guard first on `PATH`:

```bash
PATH="$PWD/.github/actions/setup/no-node:$PATH" bun run check
```

`bun run test:compat` needs Chromium, Firefox and WebKit: the Playwright projects `firefox`, `webkit`, `webkit-phone` and `firefox-tablet-dark` run the Dashboard specs in the other two browsers. `playwright:install` downloads the builds that Playwright pins, and on Linux `bunx --bun playwright install-deps firefox webkit` installs the system libraries Firefox and WebKit need. `DAVLOOM_CHROMIUM_PATH` can point the Chromium projects at a Chromium that is already installed. The cases that need a real Cloudflare deployment show as skipped, locally and in CI. `playwright:install` also deletes the builds it takes for unused from the directory it installs into, which can be one that another checkout's Playwright version still needs; `PLAYWRIGHT_BROWSERS_PATH` gives a checkout a browser directory of its own.

## Coverage gates

`vitest.config.ts` keys each package's thresholds by its `src` glob, such as `packages/core/src/**`. A package starts at the coverage measured when its gate was added. Its thresholds then only go up, toward the V1 targets in section 11 of the PRD, and lowering one needs a reason in the `design.md` of the change that lowers it. `scripts/coverage-thresholds.test.ts` fails when a package under `apps/` or `packages/` has no `src` directory or no thresholds, and when a package that the PRD's Coverage Gates table names has a threshold below its V1 target. Since 2026-11-24 every package is at or above its target. `packages/storage`, which the table does not name, gates 99% of lines, 92% of branches and 98% of functions: its Durable Objects adapter and R2 driver used to run only in workerd, and their cases now also run with the unit tests on Bun, the adapter on `bun:sqlite` through a stand-in object state and the driver on an R2 bucket in memory (`packages/storage/test/`). `test:storage` still runs the same cases in workerd, which stays the reference for the platform's behavior.

`bun run test:coverage` prints a row for each file and package. When a package falls below a threshold, it exits with a non-zero status and names the package and the metric. It also writes `coverage/coverage-summary.json`, which `bun run coverage:summary` turns into the table that the `coverage` job adds to its summary: each package's lines, branches, functions and statements, with the covered and total counts and the threshold. The table command fails too when a package is below a threshold. Vitest writes no report when a test fails, and the summary then says so in place of the table.

## Vulnerable dependencies

The `dependencies` job fails when OSV-Scanner finds a published vulnerability in any package that `bun.lock` resolves. The log lists each one with its OSV URL, which ends in the vulnerability's ID, and with the package, its version and the first fixed version. A vulnerability published today fails every pull request until it is dealt with, and the weekly run fails on `main` as well.

Fix it first. `bun why <package>@<version>` shows which dependency pulls the vulnerable version in, and an update of that dependency to its npm `latest` release often brings the fixed version.

When no `latest` release fixes it and the vulnerable code does not run in Davloom, register an exception in `osv-scanner.toml`:

```toml
[[IgnoredVulns]]
id = "GHSA-67mh-4wv8-2f99"
effectiveUntil = 2027-02-19
reason = "Why the vulnerable code does not run in Davloom, and what will remove the exception"
```

The `id` comes from the log. `effectiveUntil` is the date when someone has to look again, a few months out; once it has passed, the scan fails again, and the exception is either renewed with a current reason or removed. With the exception in place, `bun run scan:deps` prints the vulnerability with the words "has been filtered out because" and the reason, and passes. OSV-Scanner 2.7.1 deprecates the older key `ignoreUntil` and warns on every scan that uses it. The repository keeps one exception today: GHSA-67mh-4wv8-2f99 in esbuild 0.18.20, which `drizzle-kit` 0.31.11 brings in through `@esbuild-kit/esm-loader` but never loads. drizzle-kit bundles tsx and runs esbuild 0.25.12, which has the fix.

## Dependency updates

Renovate opens the pull requests that move dependencies to their npm `latest` releases, following `renovate.json` (Decision 3 of `add-ci-baseline`). It runs as the Renovate App once a maintainer has installed it on the repository, which is task 6.2, and it reads `renovate.json` from `main`.

- A dependency moves on Renovate's first run after its release, with no waiting period and no schedule, and its version stays exact, as `exact = true` in `bunfig.toml` keeps it for `bun add`. A pre-release version counts once the npm `latest` tag points to it, as Dependencies in `CLAUDE.md` says. Each npm package at or below `latest` gets one update, straight to `latest` even across a major version, so an update never stops at a pre-release that `latest` does not point to. Renovate drops the `latest` limit for a package whose version is already above `latest`, so a package that the owner allows above it needs a `followTag` rule of its own, as Miniflare has below. Nothing merges itself: a Renovate pull request needs two approvals or the owner's merge (Pull requests in `CLAUDE.md`). Renovate keeps at most 10 update pull requests open, sets no limit on vulnerability fixes, and has no hourly limit.
- The Dependency Dashboard, an issue that Renovate keeps up to date, lists every pending update and the OSV vulnerabilities of the direct dependencies. Transitive dependencies get their fixes through Lock File Maintenance, which refreshes `bun.lock` every Monday before 04:00 UTC, and the `dependencies` job reports whatever is left.
- A vulnerable direct dependency gets a pull request of its own, with `[security]` at the end of its title, which moves it to its newest version rather than the first fixed one. Renovate opens every vulnerability fix outside its group and outside the group's `allowedVersions`. So before a fix to a package in any group merges, a monorepo group such as Vitest's included, the group's other packages join it at matching versions, or the fix is closed in favor of the group's own update; a StyleX fix outside the Astryx range fails `check` as any StyleX update outside it would.
- An action stays pinned to a full commit SHA, and Renovate updates the SHA and the version comment after it together.
- Some packages move together, one pull request per group: the Astryx packages; the StyleX packages; Wrangler, Miniflare and `@cloudflare/vitest-plugin`; and the packages of each monorepo that Renovate's `group:monorepos` preset lists, among them Effect, Vitest, Playwright, Better Auth, and TanStack Router with TanStack Start. `@tanstack/react-store` and `@tanstack/charts` belong to no group and move on their own.
- StyleX stays inside the range of `@stylexjs/stylex` that `@astryxdesign/core` declares, `^0.19.0` today, through `allowedVersions` in `renovate.json`.
- Miniflare follows its `beta` tag, under which each Wrangler release publishes the Miniflare it pins. The group therefore gives Miniflare the version that the new Wrangler pins, as the standing exception in Dependencies in `CLAUDE.md` asks. A Renovate run in the minutes between a Miniflare beta and its Wrangler release proposes Miniflare alone, and the next run adds Wrangler. Once Miniflare's own `latest` tag reaches the version that Wrangler pins, remove the rule, because a followed tag that stops moving would leave Miniflare on its last beta.
- `renovate.json` extends `config:recommended`, but replaces its `ignorePaths` with `**/node_modules/**` alone. The preset skips every `tests/` directory, and `tests/integration/compat` is a workspace with dependencies of its own.
- Commit subjects and pull request titles read `fix(deps): update <package> to v<version>` for runtime dependencies and `chore(deps): ...` for the rest, all in lower case. Across a major version the subject names only the new major, as in `update <package> to v<major>`. A group's subject names the group, as in `chore(deps): update wrangler`, and leaves the version out when the group's packages move to different versions. A long package name or the `[security]` suffix of a vulnerability fix can still take a subject past the 50 characters that `.gitmessage` allows.

Renovate does not update the tools that `scripts/lib/tools.ts` pins, because they are not npm packages; Pinned tools above says how to move one.

After changing `renovate.json`, validate it from the repository root:

```bash
bunx --bun --ignore-scripts -p renovate renovate-config-validator --strict
```

`--strict` also fails on an option that Renovate has renamed or moved. `--ignore-scripts` keeps the install from building the native `re2` module, which crashes Bun 1.4.4 when it loads; without that module the validator falls back to JavaScript regular expressions and prints a warning saying so. `dependencyDashboard` is an object, the form that Renovate has read since 44.232.0.

### Upgrading StyleX with Astryx

When an Astryx release changes the StyleX range of `@astryxdesign/core`, its Renovate pull request fails the `check` job, because the installed StyleX no longer satisfies the new range. The fix goes into that pull request:

1. Set `allowedVersions` of the StyleX rule in `renovate.json` to the new range.
2. Set `@stylexjs/stylex` in `apps/web/package.json` and `packages/ui/package.json`, and `@stylexjs/unplugin` in `apps/web/package.json`, to the newest version inside the new range.
3. Run `bun install`, then `bunx --bun astryx upgrade --from <the Astryx version before the update> --apply`.
4. Run `bun run check` and `bun run test:compat`, and push to the same pull request.

## Secret findings

The `secrets` job fails when Gitleaks finds something that looks like a credential in a commit. The log names the rule, the file, the line and the commit, shows `REDACTED` in place of the value, and gives the finding's fingerprint.

If the value is a real credential, revoke it at its provider first. The repository is public, and GitHub keeps a pushed commit readable by its SHA, and in the pull request's timeline, even after a force-push removes it from the branch. Then take it out of the branch.

If the value only looks like a credential, such as a test value, change it to one that Gitleaks does not flag, or end its line with a `gitleaks:allow` comment, which makes Gitleaks skip that line. The job scans every commit that the pull request adds, so the change goes into the commit that added the value, by amending it; a later commit that changes the line leaves the finding in place. A finding in a commit already on `main` goes into `.gitleaksignore` as its fingerprint, on a line of its own, with a comment above it that says why. A fingerprint names the commit's SHA, so it stops matching once GitHub rebases a pull request, and it suits only commits on `main`. The allowlist in `.gitleaks.toml` holds only the secret that the compatibility tests give Better Auth, and nothing else goes there.

Before pushing, `bun run scan:secrets --log-opts=origin/main..HEAD` scans the commits that are not on `main` yet. That covers what the job scans for a pull request, and on a stacked branch also the commits of the pull requests below it.

## Workflow checks

The `workflows` job runs two tools on `.github`, and fails when either finds a problem; zizmor runs after an actionlint failure too, so one run reports both.

- actionlint checks each workflow's syntax and its expressions, the needs between jobs, and the inputs a step passes to an action, local ones included, and names the file, line and column of each error. It runs with `-shellcheck=` and `-pyflakes=`, which turn off the checks it would delegate to ShellCheck and pyflakes: the runner image ships ShellCheck 0.9.0, a version no pin controls, and a Mac usually has neither, so the same command would report different problems in the two places. actionlint reads a local action's `action.yml` for its inputs, and fails on one it cannot parse, but does not check the steps inside it. It needs a Git checkout: in an export without `.git` it exits with status 3.
- zizmor audits the workflows and the local actions for security problems. Among them: an action referenced by tag or branch rather than a full commit SHA, a workflow without `permissions`, a `pull_request_target` trigger and an expression that injects untrusted input into a script. `--offline` keeps it from calling GitHub's API, so it gives the same result with or without a token. It also turns off the audits that need that API, among them `impostor-commit` and `ref-version-mismatch`, so CI does not notice a pinned SHA whose version comment is wrong; Renovate will update the SHA and the comment together once tasks 6.1 and 6.2 of `add-ci-baseline` have set it up. `--strict-collection` makes a file it cannot parse fail the job instead of being skipped with a warning. `.github/zizmor.yml` turns off one audit, `self-repository`, which asks for `uses: $/...` in place of `uses: ./...`. actionlint 1.7.12 rejects that syntax, and with `./` it checks the inputs of the local setup action.

A finding that is a false positive gets an inline `# zizmor: ignore[<audit>]` on its line, with a comment above it that says why, as the `GITHUB_PATH` line in `.github/actions/setup/action.yml` has. Fix every other finding.

`scripts/workflow-secrets.test.ts`, which runs with the unit tests in `check`, fails when a workflow or a local action reads a secret other than `GITHUB_TOKEN`: by name inside an expression, through any other use of the `secrets` context inside one, such as `secrets[matrix.name]`, or with `secrets: inherit`. GitHub accepts the `secrets` context only inside `${{ }}`, so a path such as `config/secrets.txt` in a script does not count. The test reads each file as YAML, as GitHub does: an expression in a shell comment inside `run:` counts, because GitHub expands it before the shell starts, while a YAML comment does not, and a file that is not YAML fails the test under its own name. A pull request from a fork gets no repository secrets, so a check that read one would pass on a branch and fail on a fork.

## Target job layout

By V1 a pull request runs about 20 jobs (Decision 10 of `add-ci-baseline`). The estimates below scale measurements on the M4 Pro by the factors above: 1.5 to 1.8 outside Playwright, instead of the 2 to 2.5 that Decision 10 first assumed. That multiplies its first estimates for `check`, `coverage`, the contract jobs, the deployment jobs and the migration job by about 0.73. Browser jobs are estimated at 1.2 s per run for each of their 2 workers, against the 2 to 3 s per test first assumed. The `compat` row is a measurement, and CodeQL and the scans keep their first estimates until they have run on CI.

| Jobs                                   | Contents                                                                                                                                                  | Estimate per job                                                 |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `check`                                | Lint, format, types, unit tests and build, plus the Bend proofs and the requirement coverage check from Phase 1; uploads the web build for the other jobs | 4–4.5 min, more once the Bend proofs land                        |
| `coverage`                             | Unit tests with the coverage gates                                                                                                                        | 2–3 min                                                          |
| 2 contract jobs                        | Storage and database contracts                                                                                                                            | 2–3 min                                                          |

| Migration                              | Data migration                                                                                                                                            | About 3 min                                                      |
| 6 browser shards                       | Playwright, 2 workers per shard                                                                                                                           | 4–6 min                                                          |
| `compat`                               | Phase 0 compatibility tests                                                                                                                               | 6.5 min today, while it still runs the dashboard's browser tests |

The browser shards and the deployment jobs wait for the web build from `check`, so a pull request should take about 10 to 12 minutes of wall-clock time and about an hour and a half of runner time. Standard runners are free for public repositories, but a free account runs at most 20 jobs at once, so a second pull request at the same moment queues part of its jobs. Each phase that adds tests measures its jobs again and updates this page.
